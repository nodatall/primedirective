# Split Draft Creation From Clarifier Refinement

Goal: Add a `draft-builder` skill that synthesizes rough source material into one faithful starting draft, and narrow `clarifier` to feedback-first critique and bounded editing of supplied language.

## Context

- Route by the requested transformation, not by whether the input looks rough or polished. Draft Builder owns synthesis or reconception into a new coherent draft. Clarifier owns critique or editing of supplied language while preserving its current communicative job.
- Draft Builder returns one structurally complete, readable starting draft. It is unfinished because consequential choices remain visible and the user has not approved it—not because the prose is deliberately weak or full of placeholders.
- Clarifier returns `Feedback` by default. It produces rewritten prose only when the user explicitly requests an edit or rewrite, and it produces multiple versions only when the user explicitly requests variants.
- Explicit `$draft-builder` or `$clarifier` invocation is authoritative. When the requested operation falls outside the invoked skill's boundary, that skill should explain the boundary and recommend the appropriate route rather than silently switching contracts or performing the other skill's work.
- Both skills must preserve the user's facts, uncertainty, ownership, distinctive language, and authorization boundaries. Neither may invent evidence, polish uncertainty into confidence, or import repository facts into prose without permission.
- Evidence collection is conditional. Source registries, claim checks, and external research belong only to substantial factual or source-backed writing, not every voice dump, message, or paragraph edit.
- Simple work must stay simple. A short transcription cleanup or local edit should not automatically launch agents. Parallel direction search is reserved for substantial draft-building work with genuinely competing supported centers.
- Clarifier's current custom hook counts two named worker launches and blocks completion based on response headings. The new design removes that semantic stop gate instead of replacing it with another heuristic quality gate.
- The baseline behavior, evaluator, and scenario contract must be frozen before either skill contract changes. Draft Builder has no same-skill baseline, so its evidence must distinguish matched Clarifier regression, legacy-route migration, and candidate-only routing and contract checks for both writing skills.
- This repository does not yet have `docs/ARCHITECTURE.md`. The implementation must add a narrowly scoped architecture record for the writing-skill boundary, dispatch, validation, packaging, and installation flow before or alongside the boundary change.
- Keep fidelity rules local to Draft Builder and Clarifier in this change. Do not create a shared writing reference; record any demonstrated duplication as follow-up work.
- The unrelated Deliver-eval worktree state recorded in `tasks/tmp/finalization-baseline-draft-builder-clarifier-pipeline.status` is outside this plan and must remain untouched.

### 2. Add the Draft Builder skill

- [ ] Create `skills/draft-builder/SKILL.md` with a precise transformation-based trigger, goal, source hierarchy, voice-preservation rules, response shape, and stop condition. Do not reuse the reserved Roughdraft name or CriticMarkup workflow.
- [ ] Implement this bounded pipeline in order: reconstruct the brief and lock the supplied facts, uncertainty, ownership, must-keep language, audience, and purpose; determine whether the communicative center is clear; lock it immediately when clear; when genuinely ambiguous, consider at most two or three source-anchored centers locally or in one bounded parallel wave; select one center; choose a simple structure; draft once; critique fidelity, support, voice, repetition, and unresolved decisions; repair material issues in one bounded local revision; then recheck and stop. After the recheck, remove or revert any remaining unsupported or fidelity-violating wording without another worker wave, and surface remaining evidence or user-decision gaps under `Still unresolved`.
- [ ] Return one `Starting draft`. Add a short `Still unresolved` section only when a real thesis, audience, evidence, attribution, or scope decision remains. Do not manufacture variants, diagnoses, questions, or unresolved items to fill headings.
- [ ] Use one local pass for straightforward inputs. For substantial ambiguous inputs, permit at most one parallel wave of two fresh direction workers, require source anchors, synthesize in the parent, and proceed locally if a worker is unavailable. Worker count is a budget, never a completion condition.
- [ ] Add conditional factual-work behavior: inspect supplied or authorized sources, distinguish source facts from inference, track load-bearing claims when needed, and surface unresolved support. Do not browse, build a claim ledger, or add citations for ordinary personal drafting unless the request requires them.
- [ ] Keep consequential choices visible without pausing before the best safe starting draft. Do not publish, send, silently save as final, or otherwise treat the draft as approved output.

### 3. Narrow Clarifier to feedback and bounded refinement

- [ ] Rewrite `skills/clarifier/SKILL.md` so its trigger and goal cover critique, feedback, tightening, local editing, and explicitly requested revision of supplied language—not first-draft creation or broad thought development.
- [ ] Make `Feedback` the only default visible mode: return a small number of prioritized observations about the supplied text. Do not return alternative drafts, replacement passages, generic new directions, or an `Ideas` mode unless the user explicitly asks for those things.
- [ ] For an explicit rewrite, return one revision only. Do not add a second version, a critique, or a list of defects the revision already fixed unless the user explicitly requests both feedback and rewriting. Produce multiple versions only when the user explicitly requests variants.
- [ ] For an explicit phrase- or sentence-level edit, return only the edited unit with at most one brief explanation. Do not invoke a whole-draft pipeline for local work.
- [ ] Keep the private critic decision separate from the reviser action: identify the few material meaning, structure, support, fidelity, voice, or sentence-craft issues first; revise only when the request authorizes it; permit at most one local repair and one recheck, then stop. After the recheck, revert any remaining unsupported or fidelity-violating edit, surface evidence or user-decision gaps, and return feedback or boundary guidance instead of starting another rewrite cycle.
- [ ] Preserve the immediate supplied language as the semantic boundary. Keep outside facts as optional suggestions unless the user authorizes expansion, and retain the safeguards for personal voice, resume ownership, honest uncertainty, semantic duplication, unsupported metrics, and generic AI-polished language.
- [ ] Remove the universal `faithful-thesis` and `buried-tension` wave. Let ordinary feedback and edits use a constrained local pass; use at most one fresh specialist review only when factual risk or draft complexity makes it materially useful.
